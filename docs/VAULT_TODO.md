# Vault — изолированный подписывающий origin

Рабочий документ. Зачем нужен, как устроен, что делать по шагам.

Статус: **прототип работает**. Код — в этом репо, состояние и правила там же:
`README.md`. Этот документ остаётся про «зачем» и «куда дальше».

Домен выбран: **`sign.alcor.exchange`** (локально `sign.localhost:8443`). Имя
описывает действие, а не содержимое, одинаково годится для «sign in» и «sign
transaction» и сопротивляется расползанию: портфель на `sign.` не положишь.

---

## 1. Задача

Дать юзерам WAX/XPR торговать на Telos без установки кошелька и без создания
аккаунта руками. Passkey вместо сид-фразы, сессия вместо подписи на каждую сделку.

Проблема, из которой всё вырастает: **passkey подписывает 32 непрозрачных байта**.
Авторизатор показывает только origin, о содержимом транзакции — ничего. Значит XSS
на торговой странице может в любой момент вызвать `credentials.get()`, юзер
тачит Face ID по привычке, и подписывается `updateauth` со сменой owner.

Anchor и WAX Cloud Wallet показывают экшены перед подписью — у юзера есть шанс
прочитать. У passkey этого шанса нет вообще. **В этом измерении passkey строго хуже
Anchor**, и это надо компенсировать архитектурой.

---

## 2. Что от чего защищает

| Угроза | Чем закрывается |
|---|---|
| Классический XSS | CSP + изоляция origin |
| Злой npm-пакет в дереве app | **Изоляция origin** (vault не грузит бандл app) |
| Компрометация PostHog | Изоляция origin + убрать его с торговых страниц |
| Кража сессионного ключа | non-extractable CryptoKey + 2-of-2 + лимиты релея |
| Подменённая транзакция | Классификатор vault + экран подтверждения |
| **Захват Cloudflare / GitHub** | ⚠️ изоляция origin **НЕ спасает** → релей + таймлок + оповещение вне веба |
| Малварь на машине юзера | Ничего в браузере; passkey в Secure Enclave ограничивает |

Прецеденты, на которые опираемся (всё это реально происходило):

- **BadgerDAO, дек 2021** — скрипт в фронтенд через угнанный Cloudflare API-ключ, **~$120M**. Код в гите был чистый.
- **Curve, авг 2022** — перехват DNS, ~$570K.
- **Ledger Connect Kit, дек 2023** — бэкдор в npm-пакете, задело сотни dApp'ов.

Ни одного классического XSS. Вектор везде — цепочка поставок, CDN, DNS.

## 3. Три компонента

```
app.alcor.exchange            vault.alcor.exchange           relay (свой сервер)
Nuxt, ~1500 пакетов           8 пакетов, без сборки          вне Cloudflare
                                                              
собирает экшены      ──→      классифицирует                 цена против пула
рисует терминал               рисует подтверждение           лимиты, частота
НЕ держит ключей              держит passkey + ключи   ──→   косайн 2-of-2
                              подписывает                    kill switch
                                                              телеметрия отказов
```

Ключевое свойство, на котором всё держится: **`PUB_WA_` ключ привязан к точному
origin**. Чейн сверяет origin из `clientDataJSON` с rpid, зашитым в ключ. XSS на
`app.alcor.exchange` не может получить assertion для credential с
`rpId = vault.alcor.exchange` — браузер просто не найдёт подходящий credential.
Это отказ на уровне API, а не эвристика.

## 4. Проверенные факты по чейну

Проверялось через `get_activated_protocol_features` 22.09.2026.

- ✅ **`WEBAUTHN_KEY` активен на Telos и на WAX** → `PUB_WA_` ключи чейн принимает.
- ❌ **`DISABLE_DEFERRED_TRXS_STAGE_1` и `STAGE_2` активны на Telos** → отложенные
  транзакции мертвы. Значит `wait_weight` / `delay_sec` в authority **не работает**,
  нативный таймлок на смену owner невозможен. Только свой guard-контракт.
- ✅ **`FIX_LINKAUTH_RESTRICTION` активен** → `linkauth` нельзя повесить на
  `updateauth`, `deleteauth`, `linkauth`, `unlinkauth`, `canceldelay`. Кастомный
  permission **физически не может менять права**. Эскалация до owner невозможна
  без passkey — это гарантия протокола, не наша конфигурация.
- ⚠️ `linkauth` ограничивает `eosio.token::transfer` целиком, **задать «только этим
  получателям» на уровне чейна нельзя**. Проверка получателя существует только
  внутри vault. Другого места для неё нет.

## 5. Permission-схема

```
telos аккаунт
├── owner    → PUB_WA_ (passkey)         восстановление, редко
├── active   → PUB_WA_ (passkey)         вывод, смена прав
└── trade    → threshold 2               торговля
    ├── PUB_R1_ (сессионный)   weight 1
    └── alcorrelay@cosign      weight 1
```

Что даёт:

- Украденный сессионный ключ — половина подписи, сам по себе бесполезен.
- **Отзыв мгновенный**: релей перестаёт косайнить. Без транзакции в чейне.
  Это и есть «сессия на 24 часа» — нативного expiry ключей в Antelope нет.
- Релей — первый авторайзер через `noop`, поэтому **CPU/NET платит он**
  (`ONLY_BILL_FIRST_AUTHORIZER` активен). Уже реализовано в `CpuPayerWrapper`.
- Релей **не кастодиан**: без ключа юзера подписать не может.

Аккаунты: создаёт бэк лениво, при первом депозите. RAM платит Alcor.
**`owner` сразу на passkey юзера, не на бэк** — иначе мы кастодиан со всеми
регуляторными последствиями, при нулевой разнице в UX.

## 6. Сессионный ключ

```js
const kp = await crypto.subtle.generateKey(
  { name: 'ECDSA', namedCurve: 'P-256' },   // R1, не K1 — WebCrypto умеет только P-256
  false,                                     // extractable: false
  ['sign']
)
await idbPut('session-key', kp.privateKey)   // CryptoKey структурно клонируем
```

`extractable: false` — приватный ключ недостижим для JS. XSS может попросить
подписать, пока вкладка открыта, но **не может вынести ключ**.

Оговорки, спроектировать заранее:

- Умирает вместе с site data (чистка, приватное окно).
- **Safari ITP сносит всё script-writable хранилище через 7 дней** без визита.
  `navigator.storage.persist()` помогает на Chrome/Firefox, на Safari нет.
- Не синкается между устройствами и браузерами.
- **Аппаратной защиты нет** — лежит в профиле браузера на диске. От скрипта защищён,
  от малвари с доступом к файлам — нет. Аппаратно защищён только passkey.

Всё это не страшно: ключ — расходник, потеря = один тач Face ID.
**Ничего невосстановимого туда не класть.**

## 7. Протокол app ↔ vault

**Формат — сырые Antelope-экшены.** Не свой DSL: что показано, то и подписано,
нет зазора перевода. App может выкатывать новые фичи без релиза vault.

**Передача — popup, не iframe.**

```js
window.open('https://vault.alcor.exchange/confirm?rid=' + reqId,
            'alcor-vault', 'width=420,height=640')
```

Почему popup:

- iframe можно сделать прозрачным, 1×1, подсунуть под курсор — геометрией управляет
  заражённая страница.
- **В iframe нет адресной строки** → XSS может нарисовать свой «диалог vault»
  обычным HTML, юзер не отличит.
- В отдельном окне юзер видит настоящий `vault.alcor.exchange` с замком.
- Открывать по клику юзера → блокировщик попапов не мешает.

**Экшены передавать через релей по `reqId`, не в URL.** App кладёт, vault забирает
сам. Тогда в адресной строке нет ничего, чем можно манипулировать.

Если всё-таки iframe: `frame-ancestors` в CSP + `IntersectionObserver` v2
(`trackVisibility: true`), кнопка неактивна пока обсервер не подтвердит, что элемент
виден и не перекрыт. Это заплатка, popup решает целиком.

## 8. Классификатор — самое важное место

Маленький (страница кода), но ошибка в нём стоит всего. **Ревьюить отдельно.**

### Почему нельзя по `action.name`

На Alcor **вся торговля — это `eosio.token::transfer`**:

```
AlcorTradingAdapter.ts:265   transfer   лимитный ордер
AlcorTradingAdapter.ts:353   transfer   маркет
useSwap.ts:381               transfer   своп
useStaking.ts:350            transfer   стейкинг
useOtcActions.ts:62          transfer   OTC
telos-bridge/antelope.ts:158 transfer   бридж
```

И кража — тоже `transfer`. Один экшен, один контракт. Классификация по имени
либо заблокирует всю торговлю, либо пропустит всё.

### Различают три поля

```js
{
  account: 'eosio.token',              // какой токен
  name: 'transfer',
  data: {
    to: 'alcorammswap',                // КУДА уходят деньги
    quantity: '1111.0000 WAX',
    memo: '450.0000 USDT@usdt.alcor'   // СКОЛЬКО получим взамен
  }
}
```

`memo` — не служебная строка, а **вторая половина сделки**. Формат из
`lib/alcor/antelopeAsset.ts:61`: `<asset>@<contract>`, где asset — запрашиваемая
сумма. **`ask = 0` означает маркет-ордер, «беру любую цену»**
(`AlcorTradingAdapter.ts:350`).

Атака, которая проходит проверку только по `to`:

```js
to:   'alcorammswap',              // ✅ в allowlist
memo: '0.0000 USDT@usdt.alcor'     // маркет по любой цене
```

Получатель идеальный, vault доволен, атакующий ловит слив своим встречным
ордером по мусорной цене.

### Правила

1. **Allowlist, не denylist.** Дефолт — показать. Неизвестное — показать громко:
   «Alcor не распознал эту операцию».
2. **Решение по транзакции целиком, не по экшенам.** `[swap(честный),
   transfer(всё→хакеру)]` — одна неопознанная → вся транзакция на экран.
3. **Сравнивать `(account, name, to)` кортежем**, не один `to`. Иначе
   `alcorammswap::withdraw` тоже «к своему контракту» и проедет.
4. **Список имён захардкожен и точен**, без суффиксных матчей `*.alcor`.
5. **`authorization` проверять на каждом экшене** — `actor` тот, `permission` тот.
6. **Сериализует vault своей ABI**, захардкоженной для контрактов из allowlist.
   Апгрейд контракта не должен незаметно менять смысл полей.
7. **Транзакцию собирает vault**: `expiration` и TAPOS со своего RPC,
   `context_free_actions: []`, `transaction_extensions: []`, `delay_sec: 0`
   принудительно. Context-free actions от app не принимать никогда.
8. **Метаданные с чейна, не из экшена.** `symbol` и `decimals` vault берёт сам либо
   держит захардкоженными — иначе покажет «100 USDT» там, где сто миллионов юнитов.

### Тихий набор задаётся границами, а не адресом

Молча подписывается только то, на что юзер согласился заранее (сумма, срок, рынки).

- **Маркет-ордер (`ask = 0`) в тихий набор не входит никогда** — это согласие на
  любую цену, у него нет нижней границы по определению. Либо экран, либо отдельный
  маленький потолок («до $200 молча»).
- **Лимитник самоограничен** — memo и есть цена. Можно молча в пределах бюджета.

Побочно решает старую тревогу: слить депозит маркет-ордерами в тишине нельзя.

### Грамматика memo своя у каждого контракта

Найдено на реальной транзакции прототипа. Спотовый DEX кладёт в memo голый
`<asset>@<contract>`, а AMM — свой формат:

```
swapexactin#<пул>#<получатель>#<минимум>@<контракт>#<дедлайн>
```

Одним разбором это не покрывается — нужна **таблица распознавателей**, и
неизвестный формат обязан остаться неизвестным, а не быть разобранным неверно.

Два следствия, оба важные:

- **Ноль на месте запрашиваемой суммы означает «любая цена» в обеих грамматиках.**
  В споте это маркет-ордер, в AMM — своп без защиты от проскальзывания. Ловить
  надо оба, и ни один не имеет права попасть в тихий набор.
- **Получатель свопа живёт в memo, а не в полях экшена.** Подменили одно слово —
  `to` по-прежнему выглядит правильно, а полученное уходит другому аккаунту.
  Проверка «получатель == подписывающий» существует только внутри vault.

### Кто что проверяет

| Проверка | Где | Почему |
|---|---|---|
| `to` в allowlist, memo парсится, токен известный, бюджет | vault | дёшево, без сети |
| Спот: memo против лучшего бида/аска | vault | один `get_table_rows`, ~30 строк |
| AMM: цена против пула (концентрированная ликвидность) | **релей** | тики и математика пулов — в vault не тащить |
| Частота, объём за период, аномалии | релей | нужно состояние и история |

## 9. Главный подвох — привыкание

**Ценность окна подтверждения обратно пропорциональна частоте его появления.**

Если подтверждение на каждый свап — через неделю его перестают читать. И тогда XSS
открывает настоящий vault с интентом «всё хакеру», юзер жмёт Confirm на автомате,
и все усилия в ноль.

Поэтому не «или сессия, или подтверждение», а **оба**:

1. Юзер один раз в vault: «торговля 24 часа, до $5 000, эти рынки»
2. Vault выдаёт app сессионный ключ с этим бюджетом, релей его сторожит
3. В бюджете — **без единого клика**
4. Вне бюджета, вывод, бридж, новый адрес, смена прав — **попап vault**

Редкое подтверждение читают. Это модель agent wallet у Hyperliquid и session keys
у Solana, юзеры её понимают.

**Дифференцированное трение** внутри vault: обычный своп — компактно и одна кнопка;
перевод на незнакомый адрес — красный экран, задержка кнопки на 3 секунды, ввод
суммы руками. Дорого ровно там, где опасно.

## 10. Остаточный риск

**«XSS открывает настоящий vault с подменёнными экшенами, юзер не читает и жмёт
Confirm»** — не закрывается ничем. Ни попапом, ни CSP.

Это тот же базовый риск, что у Anchor и MetaMask — индустриальный уровень, который
и так принят. Разница с исходной точкой принципиальная: раньше XSS подписывал молча,
теперь ему нужно, чтобы юзер посмотрел на настоящее окно с настоящим доменом
и всё равно нажал.

**Захват Cloudflare** — vault подменяется вместе с app, изоляция origin не помогает.
Против этого работает только:

1. Релей (не на Cloudflare) — заметит всплеск, перестанет косайнить
2. Guard-контракт с таймлоком на смену owner — 24 часа на отмену
3. **Оповещение по каналу вне веба** (телега/почта): «запрошена смена ключа».
   Без п.3 п.2 бесполезен — юзер просто не узнает.

## 11. Требования к самому vault

- **Восемь пакетов против ~1500 в app** — вот реальная цель, не ноль:
  ```
  @wharfkit/antelope + @noble/curves + @scure/bip39/bip32
    → bn.js, brorand, elliptic, hash.js, pako, tslib
  ```
  Ноль недостижим: нужна сериализация Antelope и сборка `SIG_WA_`.
- **Вендорить в репозиторий**, точные версии, никакого резолва npm при деплое.
- **Свой код не собирается вообще.** В проде лежит ровно то, что прочитал глазами
  в гите.
  ⚠️ Уточнено на практике: буквально «без сборки» недостижимо. ESM-сборки wharfkit
  тянут CommonJS (`elliptic`, `bn.js`, `hash.js`, `brorand`), которые браузер
  нативным `import` не резолвит. Поэтому сборка **разовая и снаружи**: esbuild
  прогоняется руками, результат коммитится (`public/vendor/wharfkit.js`),
  версии и sha256 лежат в `vendor/HASH`, в деплое не собирается ничего.
  Это выполняет исходное намерение и заодно оставляет в силе отказ от фреймворка:
  вендор собирается раз, наш код — никогда.
- **Нативный JS, не Svelte.** Vault — список строк и две кнопки, фреймворк не
  окупается, а тулчейн Svelte вернёт ту самую прослойку, ради избавления от которой
  всё затевалось.
- **`innerHTML` не использовать нигде** — только `textContent`. С данными с чейна
  это единственное место, где в vault может завестись XSS.
- **Отдельный проект в Cloudflare, отдельная ветка.** Деплой app не должен иметь
  физической возможности тронуть vault.
- **Публиковать хеш** задеплоенного файла — проверяемо снаружи.
- **Куки не шарить**: `Domain=.alcor.exchange` запрещён.
- **Owner-операции не приходят через postMessage вообще.** Вывод и смена прав —
  юзер инициирует внутри vault, на полноценной странице. Через протокол приходят
  только торговые экшены.

## 13. Открытые вопросы

- [ ] **Домен зафиксировать ДО раскатки passkey.** `PUB_WA_` хранит rpid, чейн
      сверяет с origin. Ключ с `wax.alcor.exchange` не заработает на
      `alcor.exchange`, и `rp.id` на родительский домен это не чинит — чейн
      сравнивает с хостом origin. Идёт переезд (`legacy-redirects.ts`) → сначала
      домен, потом ключи. Иначе мёртвые аккаунты.
- [ ] Guard-контракт с таймлоком — делать сразу или когда TVL вырастет?
- [ ] Канал оповещения вне веба: телега, почта, пуш?
- [ ] Схема имён аккаунтов — от `passkeyId()` или последовательные?
- [ ] **Восстановление аккаунта.** Приватник passkey не экспортируется ничем —
      он в Secure Enclave, API для чтения не существует. Значит единственный

## 15. Прототип — как раскатываем локально

Решено 23.09.2026. Прототип живёт **на двух origin с самого начала**, а не на
странице внутри app.

```
app    https://localhost:3000        Nuxt, как сейчас
vault  http://vault.localhost:8080   статика, тупой сервер над каталогом
```

### Почему не страница внутри app

`PUB_WA_` хранит rpid, чейн сверяет его с origin из `clientDataJSON`. Ключ,
созданный на `localhost`, недостижим с `vault.localhost` и наоборот — браузер
просто не найдёт подходящий credential. **Это и есть то единственное свойство,
ради которого vault затевается**, и на одном origin его не проверить никак.
Прототип на странице в app протестировал бы всё, кроме того, что он должен
доказать.

Плюс топология сразу совпадает с продовой: vault не импортирует ничего из
бандла app, потому что физически не может.

### Почему `vault.localhost` работает

- Chrome резолвит `*.localhost` в 127.0.0.1 сам, без `/etc/hosts`. Firefox тоже.
  **Safari — нет**, ему нужна строка в hosts.
- Хосты на `.localhost` считаются potentially trustworthy, поэтому WebAuthn,
  WebCrypto и IndexedDB работают по голому http.
  ⚠️ Но ключ из этого не собрать: `webauthn.js` требует https явно
  (`WebAuthn keys require https`) и пишет в `PUB_WA_` хост origin. Так что
  **https обязателен**, и ставится он локальным `mkcert` — доверенный CA, ошибки
  сертификата нет, возражение против сертификата снимается целиком.
- Порт в rpId не участвует — rpId это только хост. Ключ с `vault.localhost:8080`
  будет работать и на `vault.localhost:9000`.

⚠️ Уверенность в `*.localhost` как в доверенном origin — по Chrome. В Firefox и
Safari поддержка мутнее. **Прототип гоняем в Chrome**, и первым же шагом
проверяем эмпирически одним вызовом `navigator.credentials.create()`.

### Почему vault не вешаем на дев-сервер Nuxt

Сертификат дев-сервера выписан на `localhost` и на `vault.localhost` не
распространяется. Через ошибку сертификата можно прокликать, но тогда origin
перестаёт быть доверенным и WebAuthn вправе отказать. Отдельный http-сервер
снимает вопрос целиком.

`window.open()` из https-страницы на http-адрес — навигация верхнего уровня,
а не подресурс, поэтому mixed content не блокируется и попап откроется.

Редиректы не мешают: в `server/middleware/legacy-redirects.ts` нет катч-олла,
только точные пути. Списка `knownPaths` в репозитории нет — строчка в `CLAUDE.md`
описывала несуществующий механизм и **поправлена**.

### Что прототип проверяет, а что нет

| Проверяется | Не проверяется |
|---|---|
| Классификатор (§8) — целиком, от origin не зависит | CSP |
| Экран подтверждения и дифференцированное трение (§9) | Отсутствие шага сборки в проде |
| Сессионный ключ, `extractable: false`, бюджеты (§6) | Разделение кук между app и vault |
| Протокол app↔vault: popup, `reqId` (§7) | Поведение под реальным Cloudflare |
| **Привязка credential к origin** — главное | Релей: цена против пула, лимиты (§8) |

### Статус тестовых passkey

Всё, что создаётся на `vault.localhost`, — **одноразовое**. На
`vault.alcor.exchange` эти ключи не поедут, и `rp.id` на родительский домен это
не чинит: чейн сравнивает с хостом origin. Тестовые аккаунты заводятся заново,
это не миграция.

Побочный эффект: passkey'и осядут в связке ключей под именем `vault.localhost`
и будут мозолить глаза — почистить руками потом.

На открытый вопрос №1 (§13) это не влияет никак: **прод-домен всё равно надо
зафиксировать до того, как первый реальный юзер получит passkey.**

## 16. Как vault входит в app — ещё один провайдер

В приложении уже есть механизм, под который vault ложится без новых абстракций.

- `types/wallet-provider.ts` — интерфейс `IWalletProvider` и тип
  `WalletProviderId`
- `composables/wallet-providers/registry.ts` — `PROVIDER_META`, список строк
  в модалке подключения
- `composables/wallet-providers/*.ts` — по файлу на провайдера

Ближайшие аналоги для чтения перед стартом:

- `WebauthProvider.ts` (176 строк) — passkey-подобный провайдер поверх внешнего
  SDK, самый близкий по форме
- `WireDevProvider.ts` (363 строки) — **testnet-only провайдер**, уже
  ограниченный одним venue через `supportedVenues`. Готовый образец того, как
  добавить кошелёк, который не должен попасть в прод-венью.

Прототип регистрируется как `id: 'vault'`, `supportedVenues: ['telos']`, ровно
как `wire-dev` ограничен `['wiretest']`. Это и есть «тестовый режим»: провайдер
физически не предлагается на тех venue, где его быть не должно.

Что провайдер делает под капотом: открывает попап vault, ждёт ответа по `reqId`,
получает identity и сессионный ключ, отдаёт терминалу `ISigner`. Подписывает не
он — подписывает vault на своём origin.

## Итоговая схема

| Компонент | Роль |
|---|---|
| **App** | собирает экшены, шлёт в vault, ключей не держит |
| **Vault** | 8 зависимостей, без сборки, свой домен. Классифицирует, рисует, подписывает |
| **Тихо** | лимитники в пределах бюджета и срока |
| **С экраном** | маркет-ордера, переводы вовне, бридж, всё неопознанное |
| **Релей** | цена против пула, лимиты, kill switch, телеметрия |

Для юзера: **один тач Face ID при входе, дальше торговля без подписей,
Face ID снова только на выводе.** Проще, чем Anchor, где каждая сделка — попап.
