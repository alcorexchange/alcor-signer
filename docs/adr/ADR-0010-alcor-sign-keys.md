# ADR-0010: Alcor Sign — ключи, корень и восстановление

## Status

Accepted — 2026-09-24

## Context

Alcor Sign (этот репо, адрес `sign.alcor.exchange`) — подписывающий origin и
основная identity Alcor. Он должен жить годами: подпись на Antelope-сетях
(Telos, XPR, WAX…), создание аккаунтов, перенос существующих аккаунтов из
других кошельков, а позже — EVM и Hyperliquid.

Прототип решал задачи по одной: passkey на active, случайный сессионный ключ в
IndexedDB, recovery-ключ из PRF отдельной солью. Для кошелька на годы нужна одна
схема, в которой ясно, откуда берётся каждый ключ, где он лежит и как
восстанавливается, если пропало всё, кроме бумажки.

Ограничения, от которых схема отталкивается:

- **Хранилища нет.** Ни у Alcor, ни у браузера нельзя держать то, без чего
  человек теряет деньги. Браузер вычищает данные сайта, бэкенд — точка захвата.
- **Passkey подписывает только P-256** и только нативно на Antelope (`PUB_WA_`).
  Всё остальное (secp256k1, Ethereum) из passkey можно лишь вывести через PRF.
- **Соль PRF вычисляется внутри аутентификатора.** JS получает результат только
  для запрошенной соли, сам секрет credential наружу не выходит. Разные соли
  изолированы железом.
- **WebCrypto не умеет secp256k1.** Неэкспортируемый `CryptoKey` возможен только
  для P-256 (и прочих стандартных кривых).

## Decision

### 1. Основа — без изменений

- Отдельный origin, rpId ровно `sign.alcor.exchange` (не `alcor.exchange`: иначе
  ассерт сможет запросить любой поддомен, включая app). Без сборки, без импортов
  из app, внешний код — только вендор-бандл с хешем.
- App присылает **экшены**. Транзакцию вокруг них собирает vault: `chain_id` из
  своего реестра, TAPOS и `expiration` со своего RPC, `delay_sec: 0`, пустые
  `context_free_actions` и расширения. Экран подписи строится из экшенов,
  раскодированных обратно из собранной транзакции; memo читает декодер того
  контракта, которому уходят деньги.
- Сети — реестр внутри vault. App только называет сеть.
- `updateauth`, `deleteauth`, `linkauth`, `unlinkauth`, `canceldelay`, `setcode`,
  `setabi` в запросе от app — отказ целиком, до экрана. Смену прав человек
  запускает только внутри sign.

### 2. Хранение

- **Секретов на бэкенде нет.** Бэкенд — только спонсор RAM при создании аккаунта
  (и релей, если понадобится).
- **`localStorage` и IndexedDB — только кеш.** Всё, что там лежит, выводится
  заново из passkey и находится на чейне.
- **PRF обязателен.** Нет PRF — «обнови браузер или используй другое
  устройство». Других веток нет.

### 3. Корень — одни 24 слова на всё

```
PRF(salt = "alcor/v1/root")  →  32 байта  =  энтропия BIP-39  →  24 слова
24 слова  →  BIP-39 seed (пустая passphrase)  →  BIP-32 master
```

- Корень **нигде не хранится**. Нужен — Face ID с солью корня, вывели,
  использовали, забыли.
- 24 слова показываются **сразу при создании** ключа, обязательно. Кнопка
  «Copy» и галка «I saved it» — без ввода слов обратно: проверка, которую
  человек проходит раздражённым, стоит больше, чем ловит. Без галки аккаунт не
  создаётся.
- Исключение — новый ключ для аккаунта, который app заводит первым депозитом
  (`login` + `create`, account factory). До депозита на аккаунте нечего терять,
  а слова — лишний экран на входе: ключи уходят в app сразу, без слов. Слова
  app просит отдельным окном (`backup`), когда аккаунт создан и на нём деньги;
  там та же галка «I saved these words». Корень тот же — слова выводятся из
  passkey в любой момент.
- Одни слова на все сети, все аккаунты и будущий EVM. Новая сеть — новый путь,
  не новая бумажка.

Всё по стандартам: BIP-39 (слова ↔ байты), BIP-32 (дерево ключей из одного
корня), BIP-44 (разметка пути), SLIP-44 (реестр номеров сетей). `m` — master-ключ,
полученный из 24 слов; всё после `m/` — дорога от него к конкретному ключу.

```
m / 44' / <coin>' / <i>' / 0 / 0
│    │       │        │     └───┴─ стандартный хвост BIP-44
│    │       │        └─────────── номер аккаунта в этой сети: 0, 1, 2…
│    │       └──────────────────── номер сети по SLIP-44
│    └──────────────────────────── разметка по BIP-44
└───────────────────────────────── master-ключ из 24 слов
```

Апостроф — жёсткий уровень: из ключа ниже нельзя вычислить ключ выше. Уровень
аккаунта жёсткий, поэтому ключ одного аккаунта не раскрывает ни корень, ни
другие аккаунты. Хвост `/0/0` — нежёсткий, как в стандарте: он раскрывает
только ветку того же аккаунта.

**Номер сети — из SLIP-44**, у кого он есть. У кого нет — `194` (EOS), как
делает большинство Antelope-кошельков. Номер записан у сети в реестре
`public/chain.js` (`slip44`) и в таблице ниже. У пользователя ничего не
хранится.

| Сеть | `<coin>` | Откуда | owner аккаунта 0 |
|---|---|---|---|
| Telos (нативный, «Zero») | 977 | SLIP-44, 2022 | `m/44'/977'/0'/0/0` |
| WAX | 14001 | SLIP-44, 2022 | `m/44'/14001'/0'/0/0` |
| EOS | 194 | SLIP-44 | `m/44'/194'/0'/0/0` |
| XPR | 194 | номера нет, запасной | `m/44'/194'/0'/0/0` |
| любая другая Antelope-сеть без номера (PulseVM…) | 194 | запасной | `m/44'/194'/0'/0/0` |
| EVM (в будущем), включая Telos EVM | 60 | SLIP-44 | `m/44'/60'/0'/0/0` |

- **Сети на `194` делят ветку.** Аккаунт `i` в EOS, XPR и других сетях на `194`
  получает один и тот же owner-ключ. Это безопасно — подпись включает
  `chain_id`, и транзакцию из одной сети не повторить в другой, — но такие
  аккаунты публично связаны общим ключом. Внутри одной сети аккаунты не связаны.
- **Номер сети не меняется никогда.** Сеть, запущенная на `194`, остаётся на
  `194`, даже если позже получит свой номер в SLIP-44: сменить путь — значит,
  что 24 слова перестанут находить аккаунты.
- EVM на стандартном пути: те же 24 слова в MetaMask дают тот же адрес.

Owner-ключи — K1: их принимают Anchor, cleos и любой кошелёк.

**Owner-ключ свой на каждый аккаунт** (свой `i`). Аккаунты публично не связаны
общим ключом. Цена — перебор номеров при восстановлении (§8).

### 4. Горячий ключ — автоподпись на Antelope

Ключ, который подписывает без Face ID. Включается по желанию, на каждый аккаунт
отдельно.

```
PRF(salt = "alcor/v1/auto/<chain_id>/<account>/<permission>")  →  секрет области (32 байта)
SHA-256("alcor/v1/auto-key" || секрет || n || счётчик)  →  скаляр P-256 (R1), n = 0…19
  →  JWK  →  importKey(extractable: false)  →  IndexedDB
```

- `<chain_id>` — hex, `<account>` — имя аккаунта, `<permission>` — `active`.
- **Соль одна на область, номер `n` — локально.** WebAuthn вычисляет не
  больше двух солей за касание: соль на каждый номер превратила бы перебор
  двадцати номеров в десять Face ID. Изоляция от корня та же — другая соль.
- **R1, не K1**: только так ключ живёт как неэкспортируемый `CryptoKey`. Байты
  существуют в JS на время вывода и выбрасываются. Публичная точка вычисляется
  вендорным `elliptic` (WebCrypto не умеет вывести её из скаляра).
- Скаляр вне `[1, n-1]` — перехеш со счётчиком, как в `recovery.js`.
- **На бумагу не идёт.** Отдельная соль — отдельная изоляция: украденный
  горячий ключ ничего не говорит о корне, а корень при торговле не вызывается.
- Хранится по области `chain_id:account@permission` (`session.js`).
- **Ставится на active рядом с остальными ключами.** `updateauth` строится из
  authority на чейне: добавляется только горячий ключ; порог, делегации,
  задержки и чужие ключи уезжают как были. Выключение снимает только его.
- Порог permission не 1 — автоподпись не включается (один ключ не подпишет).
- **Браузер очищен** — одно касание: секрет области, двадцать кандидатов,
  сверка с ключами на active. Совпал — восстановлен, без транзакции.
- **Новый ключ — случайный номер из 20.** Восстановлению номер не важен (чейн
  покажет, какой стоит), а повторное включение после кражи не вернёт
  украденный ключ.
- **Скомпрометирован** — «Replace this browser's key»: одна транзакция снимает
  текущий номер и ставит другой.
- **Горячий ключ не подписывает смену прав никогда** (`requiresPasskey`).

«Включено» — только то, что подтверждает чейн. Ключ в IndexedDB без ключа на
active — не включено, кнопки «Confirm» на экране подписи нет.

### 5. Новый аккаунт

| Permission | Ключи |
|---|---|
| owner | K1 из корня, `m/44'/<coin>'/<i>'/0/0` (§3) |
| active | Face ID (`PUB_WA_`) + горячий ключ, если включён |

Создание платит спонсор (RAM). Порядок: Face ID → PRF корня → 24 слова
(«Copy» + галка «I saved it») → транзакция создания.

### 6. Слинкованный аккаунт

Существующий аккаунт из другого кошелька (Anchor, WebAuth…). Owner остаётся у
старого кошелька.

- **Линковка**: vault отдаёт app публичные ключи — Face ID и, если галка
  включена, горячий ключ. Старый кошелёк ставит их на active **одной
  транзакцией**, добавляя к существующим (`addKeyAction`). Vault ничего не
  подписывает.
- **Recovery (опционально)**: ключ из корня со следующим `i` добавляется на
  owner рядом со старым. После этого аккаунт восстанавливается по 24 словам и
  находится поиском по корню — полностью наш.
- Подписать `updateauth` на owner должен текущий owner. Если кошелёк отказывает:
  сначала инструкция (в Anchor — «allow dangerous transactions»), запасной путь —
  импорт по ключу (§6a).
- **WAX Cloud Wallet** ключей не отдаёт. Там только Face ID на active, если
  WCW подпишет такой `updateauth` (проверить). Recovery для WCW нет.

### 6a. Импорт по приватному ключу (только Antelope)

Всё — только на sign. В app приватный ключ не попадает никогда.

1. **Passkey уже есть** (иначе сначала создание, §5 — с 24 словами). Импорт
   встаёт в существующий корень.
2. **Сеть и ключ.** Поле: `PVT_K1_…` или WIF `5…`; скрытое, без автозаполнения
   и проверки орфографии, в логи не попадает. Над полем: «вставляй ключ только
   здесь, на `sign.alcor.exchange`».
3. **Поиск на чейне.** Публичный ключ → аккаунты и permission, где он стоит.
   Ничего — отказ. Кастомные permission не трогаются, только owner и active.
4. **Выбор аккаунтов** — можно несколько, одна транзакция, по экшену на аккаунт.
5. **Что получится** зависит от того, где стоит ключ. Active может менять сам
   себя (нода требует подпись самого permission или его предка), owner — только
   owner:

   | Ключ стоит на | owner | active | Аккаунт становится |
   |---|---|---|---|
   | owner | старый + ключ из корня (следующий свободный `i`) | всё, что было, + Face ID + горячий ключ | нашим: восстанавливается по 24 словам |
   | только active | не трогаем | всё, что было, + Face ID + горячий ключ | слинкованным (§6): 24 слова его не вернут |

   Во втором случае до подтверждения — строка: «This key controls active only —
   Face ID will work, but the 24 words won't recover this account».
6. **Галка «Remove the old key»** — по умолчанию выключена. Рядом: пока старый
   ключ стоит, аккаунтом владеет и любой, у кого он есть.
7. **Подпись.** Один Face ID с солью корня — вывести owner-ключ; транзакцию
   подписывает вставленный ключ, отправляет sign. Ресурсы платит аккаунт; не
   хватает — спонсор, тот же, что при создании.
8. **Ключ забыт.** Поле очищено, переменные обнулены, нигде не сохранён.

**Вставленный ключ никогда не становится горячим.** Он K1 — неэкспортируемым
его не сделать; он не из нашего PRF — после очистки браузера не восстановить;
он чужой — неизвестно, где побывал. Горячий ключ всегда новый, из PRF (§4).

**EVM импорта нет.** Адрес — это ключ: поставить на него наш ключ нельзя, а
хранить чужой — негде. EIP-7702 не решает: старый ключ владеет адресом навсегда.
Возможен только перенос средств на адрес из корня — отдельная задача, позже.

### 7. Новое устройство (passkey синхронизировался, кеша нет)

Одно касание Face ID, в нём и PRF корня, и подпись:

- **Наши аккаунты**: корень → owner-ключи по `i` в каждой сети (§3) →
  `get_accounts_by_authorizers`. Перебор до 5 пустых номеров подряд: номер мог
  быть выделен под recovery, который так и не встал.
- **Слинкованные**: из подписи ассерта вычисляется публичный P-256 (два
  кандидата, неверный не находит на чейне ничего) → `PUB_WA_` → аккаунты, где он
  стоит на active. Этот же ключ нужен для сборки `SIG_WA_`.

### 8. Потеря passkey — переезд

Новый passkey даёт новый PRF, то есть **новый корень**. Старые 24 слова новый
passkey воспроизвести не может, а хранить их нам негде. Поэтому восстановление
— это переезд:

1. Ввод 24 слов → все старые owner-ключи (перебор `i` как в §7).
2. Новый passkey → новый корень → новые 24 слова, обязательная запись.
3. Antelope: старым owner ставим новый owner (из нового корня) и новый active
   (новый `PUB_WA_`). Аккаунт тот же, одна транзакция на аккаунт.
4. EVM (когда будет): перевод средств на новый адрес.
5. Старые слова больше не нужны.

Слинкованные аккаунты без recovery 24 словами не спасаются: их owner у старого
кошелька. Человек заходит через него и линкует заново. Экран линковки говорит
об этом одной строкой.

### 9. EVM — не на старте

- Когда появится — из того же корня, путь из §3.
- **Ключ основного адреса в браузере не хранится никогда.** secp256k1 нельзя
  сделать неэкспортируемым, а EOA нельзя отозвать: сохранённый ключ = адрес.
- Подпись основным адресом — Face ID с солью корня на каждую транзакцию.
- Автоподпись на EVM — только одним из путей:
  1. **Hyperliquid agent** — главный ключ один раз подписывает `approveAgent`,
     ключ агента из соли `alcor/v1/auto/hyperliquid/<address>/<n>`. Агент не
     может выводить средства.
  2. **Отдельный горячий адрес** из соли `alcor/v1/auto/evm/<n>`, с тем, что
     человек сам туда положил.
  3. **Smart account / EIP-7702** с P-256 session key — ключ снова
     неэкспортируемый `CryptoKey` и отзываемый.

## Consequences

**Плюсы**

- Ни одного секрета на сервере и ни одного незаменимого байта в браузере.
- Одна бумажка на всё, стандарт BIP-39.
- Горячий ключ неэкспортируемый, отзывается одной транзакцией и
  восстанавливается без бэкенда.
- Слинкованные аккаунты сохраняют свой кошелёк; ничего чужого не снимается.

**Минусы, принятые осознанно**

- **Корень привязан к первому passkey.** Потеря passkey — переезд, а не
  восстановление на месте. Синхронизируемые passkey (iCloud, Google) делают это
  редким; PRF синхронизируется вместе с credential.
- **Кто украл 24 слова — владеет всем**, во всех сетях.
- **`extractable: false` не защищает от использования на месте.** Подменённый
  код на sign может подписать горячим ключом, пока страница открыта; против
  этого — экран подписи и, в будущем, релей. Малварь с доступом к профилю
  браузера может достать ключ с диска.
- **Горячий ключ на active может всё, что может active**, включая `transfer`
  куда угодно. Ограничение — только vault: экран подписи и отказ подписывать
  смену прав.
- Устройства без PRF не поддерживаются.

## Вне этого ADR

- Зашить ABI `eosio.token` и контрактов Alcor в vault, не брать их с RPC:
  подменённый ABI сериализует не то, что покажет экран.
- Разнести код по семействам сетей (адаптер: сборка, декодеры, подпись,
  отправка, поиск аккаунтов), чтобы EVM лёг рядом, а не поверх.
- Релей и защита доставки кода (service worker, пинящий хеши подписанных
  релизов).
